## Decision recommendation

Do not implement exact ordinary ChatGPT or Work conversation focus in C2 from
the interfaces inspected here. OpenAI's public documentation does not define an
external route or CLI command for opening a private ChatGPT or Work conversation
in the Linux desktop client. The installed client has an internal `/c/<id>`
route for both modes, but its external deep-link parser does not accept that
route. Title-only selection cannot guarantee exactness; accessibility APIs
exposing stable IDs were not validated.

The installed client does recognize `codex://threads/<id>` for a Codex task.
That mechanism is actionable for further validation but is not documented as a
public interface. Accept it for production only through a separate mechanism
gate that explicitly permits a version-tested, best-effort integration and its
maintenance cost. Otherwise wait for a documented OpenAI interface.

A window-only action is a separate, honest capability. The documented
`chatgpt` command can launch the app, and the inspected single-instance path
attempts to restore, show and focus its primary window. It cannot prove which
conversation is visible. OpenAI also warns that focus can be incomplete under
native Wayland, so this fallback still needs a live environment check before it
is claimed.

## Public interface review

The [Linux desktop documentation](https://learn.chatgpt.com/docs/linux/linux-app)
documents launching the client as `chatgpt` and the optional
`--ozone-platform=wayland` flag. It calls Linux support a preview and says
window positioning and focus may not work fully with native Wayland. It does
not document conversation arguments or deep links.

The [desktop quickstart](https://learn.chatgpt.com/docs/quickstart) distinguishes
ordinary ChatGPT Chat, ChatGPT Work and Codex as different selections. The
[projects and chats guide](https://learn.chatgpt.com/docs/projects) says one
ChatGPT project can contain both Chat and Work chats, while the Codex sidebar
contains Codex chats and projects. It documents `Ctrl+K` search for prior chats,
which is useful discovery by title or phrase but does not expose a stable target
reference or guarantee exact selection.

The [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) can start and resume a
Codex thread by ID. That controls a Codex runtime and can run turns. It is not a
documented API for navigating the installed desktop GUI. Host-provided task
navigation tools have the same limitation: they are capabilities of this host,
not distributable Fleet interfaces.

## Installed-client evidence

Read-only inspection of `/usr/lib/chatgpt/resources/app.asar` found:

- The main-process parser accepts `codex:` and production `https:` inputs. For
  `codex://threads/<target>`, it returns a `localConversation` route after
  validating the target. The renderer itself generates links of the form
  `codex://threads/${threadId}` for Codex handoffs and task links.
- The renderer builds ordinary ChatGPT and Work paths as `/c/<conversationId>`
  and exposes web links as `https://chatgpt.com/c/<conversationId>`.
- For external `https://chatgpt.com/...` input, the main-process parser accepts
  shared-conversation paths, not private `/c/<conversationId>` paths. Its
  `codex://chatgpt/...` branch likewise parses shared conversations only.
- On recognized second-instance input, the main process queues the route and
  restores, shows and focuses the primary window. A successful process launch
  therefore proves at most attempted window activation until the visible route
  is checked.

These findings describe one installed binary, not a supported API. Minified,
hashed bundle filenames and parser behavior can change on any app update. Fleet
must not read the app's private state to discover IDs or couple to undocumented
IPC.

## Target acquisition

For ordinary ChatGPT and Work, a user-provided web URL can carry a conversation
ID, but the inspected Linux client does not provide a supported external route
that consumes it. Titles and search phrases are not stable identities. Automatic
discovery would require private app state or an upstream interface that was not
found, so it is out of scope.

For Codex, the client-generated deep link contains a thread ID. Fleet's own
Codex lifecycle record may also contain a session identifier, but equivalence
between that identifier and the desktop route target was not established here.
That mapping must be proven against a disposable task before implementation.

## Unmet live checks

The requested live matrix needs two explicitly authorized, non-sensitive test
targets, including duplicate titles, plus permission to change the visible
selection and minimize or close the app. No such targets were available during
this bounded run, and changing the user's current conversation was prohibited.
Consequently, the following remain unproven:

- exact selection for an existing Codex task;
- the Fleet session ID to desktop thread ID mapping;
- already-open and minimized-window activation;
- duplicate-title behavior;
- stale or unknown IDs and an unavailable app;
- ordinary ChatGPT and Work exact selection;
- actual focus behavior on this KDE Wayland session.

An accessibility prototype was not justified without disposable targets. It
would navigate the live UI. Title-based selection does not meet the exactness
criterion, while accessibility APIs that might expose stable IDs were not
validated. If the mechanism gate permits continued Codex-only investigation,
use two disposable Codex tasks and verify the visible task identity after each
route. Treat launch exit status as insufficient evidence. Do not dispatch C2
until that live result and the undocumented-interface policy are accepted.
